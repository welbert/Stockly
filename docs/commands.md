# Tauri Commands

All registered in `src-tauri/src/lib.rs` (`invoke_handler![...]`), implemented in `src-tauri/src/commands/<domain>.rs`.
Typed wrapper on the frontend: `src/lib/api.ts` — no component calls `invoke()` directly (see `call<T>()`).

Arguments are passed in camelCase on the JS side and automatically converted to snake_case for the Rust parameters (Tauri v2 default behavior) — the names below are already in Rust format.

Every mutation that isn't self-service (`update_theme`, `update_my_auto_lock`, `add_stock_entry`, `deactivate_item`) re-checks `AppState.active_user_id` against `users.is_admin` on the backend itself (`require_admin`, in `src-tauri/src/guard.rs` — shared across command modules) — the frontend hiding a button is not the real access control.

## Auth / session (`commands/auth.rs`)

| Command | Signature | Notes |
|---|---|---|
| `login` | `(user_id, password) -> UserProfile` | verifies the bcrypt hash, rejects a deactivated (`active = 0`) user, stamps `users.last_login_at = datetime('now')`, sets `AppState.active_user_id` |
| `logout` | `() -> ()` | clears `AppState.active_user_id` |
| `get_active_user` | `() -> Option<UserProfile>` | reads the current in-memory session — always `None` right after a process restart (no "remember me": this app requires a password every time the process starts) |
| `verify_password` | `(user_id, password) -> bool` | re-checks a password without changing the session. Used by the idle-lock unlock screen (own `user_id`) and by the discount-authorization modal in Venda, where a *different* admin authorizes — same command, no session side effect either way |

## Users (`commands/users.rs`)

| Command | Signature | Notes |
|---|---|---|
| `has_any_users` | `() -> bool` | drives the login screen's first-run vs. profile-picker branch |
| `list_login_profiles` | `() -> Vec<UserSummary>` | active users only, feeds the login picker |
| `list_users` | `() -> Vec<UserProfile>` | every user, admin-only, feeds the Usuários screen |
| `create_user` | `(name, password, is_admin) -> UserProfile` | no `username` argument — it's derived from `name` (`slugify` + `unique_username`, see `docs/database.md`). First user ever (`has_any_users() == false`) is forced `is_admin = true` regardless of the argument, auto-logs in (sets `active_user_id`) and stamps `last_login_at` same as `login` would; otherwise requires an authenticated admin and honors `is_admin` as given |
| `update_user` | `(id, name, is_admin, active, auto_lock_minutes) -> UserProfile` | admin-only. `username` isn't editable (assigned once at creation). The "elevate to Admin" confirmation is a frontend-only modal (`UserFormModal`) before calling this — no separate backend step. Refuses to change `is_admin`/`active` on **your own** logged-in row (`is_active_session`) — only a *different* admin can grant/revoke a role or (de)activate an account. Also refuses to demote or deactivate the **last active Admin** (`is_last_active_admin`) — otherwise nothing could unlock the app again short of editing the `.db` by hand |
| `reset_user_password` | `(id, new_password) -> ()` | admin-only, no old password required — the only way back in for someone who forgot theirs, and (deliberately) also the only self-service password change there is, since nothing else in the app lets anyone change a password after account creation. Unlike `update_user`'s `is_admin`/`active`, resetting **your own** password through this is allowed (no integrity risk the way role/active toggling has). No `resolve_admin_authorization` two-admin flow — `UsersPage` is already Admin-only, so the acting admin always self-authorizes. Logs a `password_reset` row to `audit_log` in the same transaction as the `UPDATE` (`commands::audit::record`) |
| `delete_user` | `(id) -> ()` | admin-only, hard delete. Refuses to delete your own logged-in row, same reasoning as above. Also refuses to delete the last active Admin. Fails with a foreign-key error if the user has sales/stock movements/credit payments on record (no cascade there by design) |
| `update_theme` | `(theme) -> ()` | self-service — always writes to whichever user is in `AppState.active_user_id`, never a `user_id` argument |
| `update_font_scale` | `(font_scale) -> ()` | same shape as `update_theme` — self-service, always the active session's own row. Accessibility text-size preference; only ever consumed by the frontend's own `<html>` `font-size` (`FontScaleContext`), never by PDF generation |
| `update_my_auto_lock` | `(auto_lock_minutes) -> UserProfile` | self-service equivalent of `update_user`'s `auto_lock_minutes` field — any logged-in profile (not just Admin) can change its own idle-lock timeout |
| `list_admins` | `() -> Vec<UserSummary>` | any logged-in profile, active admins only — feeds the admin picker in the discount-authorization modal (Venda) |

## Items (`commands/items.rs`)

| Command | Signature | Notes |
|---|---|---|
| `list_items` | `() -> Vec<ItemSummary>` | any logged-in profile; `categoryName` is `null` when uncategorized (LEFT JOIN) |
| `create_item` | `(code, name, category_id, cost_price, sale_price, quantity, min_quantity) -> ItemSummary` | admin-only. `code` is optional — blank/whitespace-only means "use this item's own id" (`predict_next_item_id` + `unique_code`, since the id doesn't exist until after insert). Friendly error on a duplicate explicit `code`. Prices rounded to 2 decimals (`round2`). Writes an `initial` `stock_movements` row when `quantity > 0`, and always writes an `item_price_history` row with the starting prices (unconditional, unlike the stock one — see `docs/database.md`) |
| `update_item` | `(id, code, name, category_id, cost_price, sale_price, quantity, min_quantity, active) -> ItemSummary` | admin-only, full edit **including** `quantity` directly — this is the Admin-only "ajuste de inventário"; the delta (positive or negative) is logged as an `adjustment` row. Also logs a row to `item_price_history` whenever `cost_price` and/or `sale_price` actually changes from what was stored (doubles as a pricing audit trail — who changed it, and when). Also where `active` gets flipped back to `true` (reactivating is Admin-only) |
| `delete_item` | `(id) -> ()` | admin-only, hard delete. Fails with a friendly message **only** if the item has ever been sold (`sale_items`, checked explicitly, not via a foreign-key catch) — a stock entry/adjustment or price change with no sale is still just correcting a fresh mistake, not retiring a real item. `stock_movements`/`item_price_history` rows are `ON DELETE CASCADE` and go with it |
| `add_stock_entry` | `(item_id, quantity) -> ItemSummary` | any logged-in profile, `quantity` must be `> 0`. Logged as `entry` — the everyday "recebi mercadoria" action, distinct from Admin's `adjustment` |
| `deactivate_item` | `(item_id) -> ItemSummary` | any logged-in profile can deactivate; only Admin can hard-delete or reactivate (via `update_item`) |
| `list_stock_movements` | `() -> Vec<StockMovementRow>` | any logged-in profile, same "fetch everything" convention as `list_sales`. Every `stock_movements` row ever, newest first, joined with its item/user names — the "consulta" screen `docs/database.md` registered as pending since the table was created. `item_id`'s `ON DELETE CASCADE` means the join is always valid, never orphaned by a deleted item. `saleStatus` is a `LEFT JOIN sales` on `sale_id` (`None` unless `movementType` is `sale`/`refund`) — lets a consumer tell a `sale` movement whose sale was later cancelled apart from a still-live one. Feeds `MovimentacaoEstoquePage` directly, and `ItensParadosPage` (filtered client-side to `movementType === "sale" && saleStatus !== "cancelled"`, grouped by item for its last-sale date) |
| `list_item_price_history` | `() -> Vec<ItemPriceHistoryRow>` | any logged-in profile, same convention. Every `item_price_history` row ever, newest first, joined with its item/user names. Feeds `HistoricoPrecoPage` — the row with the earliest `createdAt` per item is always that item's creation snapshot (`create_item` unconditionally writes one), which the frontend labels "cadastro do item" instead of the admin's name |
| `export_items_csv` | `(path) -> ()` | admin-only. Writes every item (active **and** inactive, for a full round-trip) as `;`-delimited, UTF-8-BOM CSV at `path` (already picked by the frontend's save dialog, `@tauri-apps/plugin-dialog`) — `;` instead of `,` so pt-BR Excel opens it correctly on double-click. On-disk row shape: `commands::items::ItemCsvFileRow` (`codigo;nome;categoria;preco_custo;preco_venda;quantidade;quantidade_minima;ativo`, `ativo` as `sim`/`nao`) — **not** the same struct as `models::ItemCsvRow`, which is the camelCase shape this command's siblings actually return over IPC; the two convert into each other only at the `csv_util` boundary, on purpose, so a header chosen for the spreadsheet can never leak into the JSON the frontend parses (this broke once already — see the type's doc comment). Uses the generic `csv_util::write_csv`, shared with future CSV exporters (e.g. Relatórios) |
| `preview_items_csv_import` | `(path) -> ItemsCsvImportPreview` | admin-only, **read-only** — parses the CSV at `path` (`csv_util::read_csv`, one `Result` per row so a malformed line doesn't abort the rest) and classifies every row against the current DB, without writing anything: matched by `code` (exact) go to `changedItems` (only if some field actually differs) or are dropped silently (no diff); unmatched rows go to `newItems`, each carrying an optional `suggestedItemId`/`suggestedItemName` when the row's name, accent/case-folded, exactly matches an existing item's (a likely typo, not auto-applied — the admin decides on the review screen); every **active** item never matched by a row's code lands in `missingItems`. Malformed/invalid rows (bad `ativo` value, negative price/quantity, blank name) go to `errors` with their line number instead of failing the whole import |
| `apply_items_csv_import` | `(decision: ItemsCsvImportDecision) -> ItemsCsvImportResult` | admin-only, the only command that writes. `decision.creates`/`updates` carry the exact field values to apply (trusted the same way `update_item` trusts an admin's form, since the review screen already showed the diff) — `updates` covers both code-matched rows and "new" rows the admin manually remapped to an existing item (`keepExistingName: true` for the latter, so a CSV typo can't rename the real item). `missingActions` applies `"zero"`/`"deactivate"` to items left out of the CSV (`"keep"` is a no-op). One transaction for the whole import. Quantity deltas are logged as `stock_movements` type `csv_import`; price changes go to `item_price_history`, same as `create_item`/`update_item`. A category named in a row that doesn't exist yet is created on the fly (find-or-create by exact name — safe since this command is already admin-only) |

## Sales (`commands/sales.rs`)

| Command | Signature | Notes |
|---|---|---|
| `create_sale` | `(items: Vec<SaleItemInput>, discount_percent, discount_amount, discount_authorizer_id, discount_authorizer_password, payment_method, client_id, credit_paid_now) -> SaleDetail` | any logged-in profile. Re-fetches each item's code/name/price/active/quantity fresh from the DB (never trusts a frontend-sent price). Validates stock, active status, and discount bounds (0-100%, or an amount that can't exceed the line/order total) per item and for the general (order-level) discount, which is applied *after* item-level discounts (sequential, not exclusive). Calls `resolve_admin_authorization` (`guard.rs`) only when at least one discount (item or general) is present — self-authorizes if the active session is already Admin, otherwise requires `discount_authorizer_id`/`_password` for a *different* admin. `client_id` is optional for every payment method (identifies the client on the sale) — `payment_method = "credit"` is the only one where it's mandatory. `credit_paid_now` (only meaningful for `"credit"`) lets the customer pay part of the debt up front — validated `< total` (paying it off in full belongs to a different payment method, not Crediário), **except** when the client already has store credit (a negative `client_balance`, e.g. from a paid sale later cancelled) covering the full amount, re-checked server-side via `commands::clients::client_balance` rather than trusted from the frontend — in that case `paid == total` is allowed, since it's the client's own existing credit settling itself, not someone typing the full amount as a workaround. Recorded as a `credit_payments` row plus a `credit_payment_allocations` row pointing at this sale, in the same transaction as the sale, so the open balance is already reduced right after commit. Commits venda + baixa de estoque (`stock_movements`, type `sale`) + numeração do recibo atomically in one transaction (receipt number: `{yyyyMMdd}{6-digit sequential}`, global and gap-free, assigned inside the same transaction). PDF generation happens *after* the transaction commits, best-effort — a failure there doesn't fail the sale (see `receipts.rs` below); `SaleDetail.receiptPdfPath` is simply `null` in that case. When a discount was authorized, also writes an `audit_log` row (`commands::audit::record`) in the same transaction |
| `get_sale_detail` | `(sale_id) -> SaleDetail` | any logged-in profile, read-only. `receiptPdfPath` always `null` (no PDF (re)generation attempted). Used by "Ver venda" in Clientes and Histórico de vendas |
| `list_sales` | `() -> Vec<SaleListItem>` | any logged-in profile. Every sale ever, newest first, no line items (a separate `get_sale_detail` round-trip once a sale is opened) — frontend filters by date range/recibo/cliente/operador client-side, same "fetch everything" convention as `list_items`/`list_clients`. Each row's `discountValue` is computed in the query itself (`SUM(sale_items.unit_price * quantity) - sales.total`, i.e. gross total with no discounts minus what was actually charged) rather than read from a column — it's the combined item-level + general discount, not just `sales.discount_amount` (which is general-only) |
| `export_sales_csv` | `(path, rows: Vec<SaleCsvRow>) -> ()` | any logged-in profile — same access as `list_sales`, which both `SalesHistoryPage` and `VendasPorPeriodoPage` already call to get `rows` in the first place. No DB access: `rows` already carries whatever's currently filtered/display-formatted on screen (`toSaleCsvRows` in `src/lib/api.ts` — pt-BR date, payment method label, "Concluída"/"Cancelada", but `total`/`discount` stay plain numbers so a spreadsheet still sums them), this command only owns the CSV file mechanics (`;` delimiter, BOM, headers) via `csv_util::write_csv`. On-disk row shape is `commands::sales::SaleCsvFileRow` (Portuguese headers), converted from the wire-shape `models::SaleCsvRow` right at that boundary — same reasoning and split as `commands::items::ItemCsvFileRow`/`models::ItemCsvRow` |
| `export_sales_report_pdf` | `(path, title, subtitle, stats: Vec<ReportPdfStatInput>, rows: Vec<SaleCsvRow>) -> ()` | the PDF counterpart of `export_sales_csv` — same access, same rows, no DB access. Built on `pdf_util::write_report_pdf`, the generic "title + stat summary + bordered table" report layout any future Relatórios PDF export reuses. **Deliberately doesn't reproduce the on-screen chart** — `genpdf` is a text/table layout library with no drawing/canvas API, so the PDF is the printable data sheet (numbers + listing), the chart stays an on-screen-only aid. `title`/`subtitle`/`stats` are whatever the calling report screen already has on hand (its header text and stat cards, unformatted-in-Rust — the frontend already shaped them for display) |
| `list_sale_items_report` | `() -> Vec<SaleItemReportRow>` | any logged-in profile, same "fetch everything, filter/aggregate client-side" convention as `list_sales`. One row per `sale_items` line (with its sale's `createdAt`/`status`, and the item's *current* category — same live join `commands::dashboard::sales_by_category`/`top_selling_items` already use, so it shares that same limitation: a later recategorization isn't reflected historically). `list_sales` only carries each sale's total, so any report that breaks sales down by categoria/item (`VendasPorCategoriaItemPage`) needs this instead |
| `list_sale_discounts` | `() -> Vec<SaleDiscountRow>` | any logged-in profile, `completed` sales only (excludes `cancelled`, same rule `discount_granted_month` uses on the Dashboard). One row per granted discount, general *or* item-level — a sale with both kinds produces two rows, not one merged row, since "Descontos concedidos"'s "Tipo" column shows one kind per row. Queried in two passes (general vs. item-level, both joined to `discount_authorized_by_user_id`) same reasoning as `list_admin_authorizations`'s multi-query split. Feeds `DescontosConcedidosPage`, which builds the "Geral (10%)"/"Item (Nome, -15%)" label text client-side from `kind`/`itemName`/`discountPercent` |
| `cancel_sale` | `(sale_id, authorizer_id, authorizer_password) -> SaleDetail` | any logged-in profile. Rejects an already-cancelled sale. Goes through `resolve_admin_authorization` (`guard.rs`) same as discount/cancel-payment — self-authorizes if the active session is already Admin, otherwise needs a *different* admin's password. Reverses stock for every line whose item still exists (`refund`-type `stock_movements` rows, `items.quantity` restored). Never touches `credit_payments`/`credit_payment_allocations`, even if this was a Crediário sale with money already applied to it — that amount simply becomes floating credit for the client. Never deletes the row — flips `status` to `cancelled` and fills `cancelled_at`/`cancelled_by_user_id`/`cancel_authorized_by_user_id`. Also writes an `audit_log` row in the same transaction |

## Reports (`commands/reports.rs`)

Generic export commands for any Relatórios screen whose aggregated shape doesn't match a dedicated Rust type (`export_sales_csv`/`export_sales_report_pdf` above stay the one exception, since "Vendas por período" exports full per-sale rows through `SaleCsvRow`, a shape worth its own type). Any logged-in profile, no DB access — the caller already has `headers`/`rows` computed on screen.

| Command | Signature | Notes |
|---|---|---|
| `export_report_csv` | `(path, headers: Vec<String>, rows: Vec<Vec<String>>) -> ()` | writes an arbitrary string table via `csv_util::write_csv_table` — unlike `export_sales_csv`, there's no wire/file-shape split needed: `headers`/`rows` are already the exact display strings to write, nothing for the backend to translate |
| `export_report_pdf` | `(path, title, subtitle, stats: Vec<ReportPdfStatInput>, headers: Vec<String>, column_weights: Vec<usize>, rows: Vec<Vec<String>>) -> ()` | same `pdf_util::write_report_pdf` layout as `export_sales_report_pdf`, fully generic. `column_weights` is the caller's call — only it knows which columns hold long, unbreakable content (see `pdf_util.rs`'s doc comment: a word too wide for its column is silently dropped, not overflowed, the failure mode found once already while tuning "Vendas por período"'s table) |
| `open_containing_folder` | `(path: String) -> ()` | opens the OS file explorer at `path`'s parent directory via `tauri_plugin_opener::OpenerExt` — the "Clique aqui para abrir a pasta" action on every export success toast (`useToast`, `src/context/ToastContext.tsx`). Any logged-in profile. `path` is wherever the frontend's own save dialog put the file, unlike `commands::receipts::open_receipts_folder`'s configurable `recibos/` dir |

## Clients (`commands/clients.rs`)

No `username`/login involved — a client is anyone identified on a sale, unrelated to `users`. Only a client with an open Crediário balance is a "devedor"; most clients never carry one at all.

| Command | Signature | Notes |
|---|---|---|
| `list_clients` | `() -> Vec<ClientSummary>` | any logged-in profile. Every client, each with `balance` computed on the fly (sum of completed Crediário sales minus `credit_payments`, never stored directly). Frontend filters/sorts client-side, same convention as `list_items`: Clientes lists everyone by default, with a filter for `balance > 0`; the Venda client picker (`PaymentModal`) matches by name over the full list |
| `create_client` | `(name, phone, reminder_date, note, birth_date, document_type, document_number) -> ClientSummary` | any logged-in profile — no admin password, deliberately. `phone`/`reminder_date`/`note`/`birth_date` are optional, blank strings normalized to `null`. `document_number` requires `document_type` (`"cpf"`/`"cnpj"`); `document_type` alone (no number) is allowed. Both normalized (`documents::normalize_document` — uppercase, mask stripped) and check-digit-validated (`documents::validate_cpf`/`validate_cnpj`) server-side regardless of what the frontend already checked. A duplicate `document_number` (unique index) comes back as "CPF/CNPJ já cadastrado para outro cliente" |
| `update_client` | `(id, name, phone, reminder_date, note, birth_date, document_type, document_number, authorizer_id, authorizer_password) -> ClientSummary` | any logged-in profile for phone/lembrete/observação/nascimento/documento. Renaming a client that currently has an open Crediário balance (`client_balance(conn, id) > 0.0`) goes through `resolve_admin_authorization` (`guard.rs`) — self-authorizes if the active session is already Admin, otherwise needs a *different* admin's password, same pattern as discount/cancelamento de venda/pagamento. The two `authorizer_*` args are ignored when that condition doesn't hold. Document validation same as `create_client` |
| `get_client_detail` | `(id) -> ClientDetail` | any logged-in profile. Adds `sales` (every sale for this client, any payment method, newest first — completed *and* cancelled; `paid`/`remaining` only carry real meaning for Crediário rows, every other method reports `paid == total`/`remaining == 0` since it's settled at sale time) and `payments` (every `credit_payments` row, newest first, each with its `allocations`: which sale(s) it was applied to and how much) to the summary fields |
| `register_credit_payment` | `(client_id, sale_ids: Vec<i64>, amount, residual_sale_id) -> ClientDetail` | any logged-in profile, no admin password. Pays off 1+ of the client's own open Crediário sales (`sale_ids`) in one event. Rejects `amount <= 0`, an empty `sale_ids`, a sale not belonging to `client_id`, a cancelled or already-quitada sale, or an `amount` above the sum of the selected sales' `remaining`. When `amount` is less than that sum, `residual_sale_id` (required, must be one of `sale_ids`) says which sale absorbs the shortfall and stays partially paid — every other selected sale is allocated its full `remaining` and fully quitada |
| `cancel_credit_payment` | `(payment_id, reason, authorizer_id, authorizer_password) -> ClientDetail` | soft-cancel of a mistakenly-registered payment (never deleted — see `docs/database.md`). `reason` is required. Reverses a financial entry, so unlike registering the payment it goes through `resolve_admin_authorization` (`guard.rs`) — self-authorizes if the active session is already Admin, otherwise needs a *different* admin's password, same pattern as discount/cancelamento de venda. Rejects a payment that's already cancelled. Now wrapped in its own transaction (previously a single plain `UPDATE`) so the `UPDATE` and the new `audit_log` row commit or fail together |
| `list_credit_sales` | `() -> Vec<CreditSaleReportRow>` | any logged-in profile. Every still-completed Crediário sale, across all clients (global version of `get_client_detail`'s `sales`, filtered to `payment_method == "credit"`, with `clientId`/`clientName` added) — only consumer is the "Inadimplência" report, which needs each client's *oldest* sale with `remaining > 0` to compute days-overdue, something `list_clients`' per-client `balance` alone can't answer |
| `list_credit_payments` | `() -> Vec<CreditPaymentReportRow>` | any logged-in profile. Every `credit_payments` row ever registered, across all clients (active and cancelled) — feeds both "Pagamentos recebidos" (`cancelledAt === null`) and "Pagamentos cancelados" (`cancelledAt !== null`), same "one command, filtered client-side per report" shape as `list_sales`/`list_stock_movements` |

## Audit (`commands/audit.rs`)

| Command | Signature | Notes |
|---|---|---|
| `list_admin_authorizations` | `() -> Vec<AdminAuthorizationRow>` | any logged-in profile. A single query against the append-only `audit_log` table (`docs/database.md`), which every admin-authorized action now writes to inline, in its own transaction, via `commands::audit::record`: desconto concedido (`create_sale`), venda cancelada (`cancel_sale`), pagamento de Crediário cancelado (`cancel_credit_payment`), senha redefinida (`reset_user_password`). Cliente renomeado com saldo em aberto is still not logged here — `commands::clients::update_client` verifies the admin password but never persists who authorized it — see `docs/future.md`'s "Auditoria" section; adding it now is just a 4th `record` call, `audit_log` itself no longer needs building for that |

## Receipts (`commands/receipts.rs`)

| Command | Signature | Notes |
|---|---|---|
| `regenerate_receipt_pdf` | `(sale_id) -> String` (file path) | any logged-in profile. Re-fetches the full sale fresh from the DB and re-renders the PDF, overwriting any previous file for that sale (same filename, derived from the receipt number, which never changes). Needed both for the "PDF failed right after commit" case and for on-demand reprints |
| `print_file` | `(path) -> ()` | any logged-in profile. Spawns `powershell -Command "Start-Process -FilePath $env:STOCKLY_PRINT_PATH -Verb Print"` — the path travels via an environment variable, never interpolated into the command string, so it can't break out via quotes/special characters. Doesn't guarantee a print dialog appears; depends on whatever's associated with `.pdf` on the user's machine |
| `open_receipts_folder` | `() -> ()` | any logged-in profile. Opens whatever `commands::receipts::receipts_dir` currently resolves to in the OS file explorer (creates the folder first if it doesn't exist yet) — the app's own default (`<db_path's parent>/recibos/`) unless an Admin configured a different one |
| `open_receipt_file` | `(path) -> ()` | any logged-in profile. Opens one specific receipt PDF with whatever's associated with `.pdf` on the user's machine — unlike `open_receipts_folder`, which reveals the whole folder. Used by Histórico de vendas' "Abrir PDF do recibo" row action, after `regenerate_receipt_pdf` guarantees the file exists |
| `get_receipts_folder` | `() -> ReceiptsFolderInfo` | admin-only, matching the rest of the "Recibo" card in Configurações. Always returns the resolved, absolute path actually in use (`path`) plus whether it's an Admin-picked override or just the app's own default (`isCustom`) — both roles still generate/print receipts through whatever this resolves to, only *choosing* the folder is gated |
| `set_receipts_folder` | `(path) -> ()` | admin-only. No validation that `path` is writable — a bad folder only surfaces as a failure toast the next time a receipt actually needs to be generated. Takes effect for the next receipt on, not retroactively — files already written to the old folder stay there |
| `clear_receipts_folder` | `() -> ()` | admin-only. Reverts to the app's own default folder — same "write an empty string" convention `set_store_name`/`set_store_info` already use, not a deleted `config` row like `clear_backup_folder` |

The PDF itself is built with `genpdf` (real vector text, not a rasterized screenshot — see `CLAUDE.md`'s Stack table), using an embedded Courier Prime font (`src-tauri/assets/fonts/`, SIL OFL license, via `include_bytes!`) and an 80mm continuous-roll page size with dynamic height — matches the thermal printer this app targets. Font loading (`font_family()`) and pt-BR money formatting (`fmt_money()`) live in `pdf_util.rs`/`money.rs` respectively, not duplicated here — `pdf_util.rs` also holds `write_report_pdf`, the generic A4 "title + stats + table" layout `export_sales_report_pdf` (Relatórios) builds on, a deliberately different shape from this receipt's 80mm layout. Layout: header (store name/info from config, falling back to "BORA VENDER"), recibo/data/operador, **cliente vinculado (only when `payment_method == "credit"`)**, itemized lines (each with its own discount noted when present — `-X%` or `-R$ Y`, matching whichever type was applied), subtotal/desconto geral/total, **"Valor pago" / "Valor devido" (only when the sale already has money applied to it)**, payment method (labeled "Crediário" for `credit`), and a configurable thank-you footer plus a line stating the receipt has no fiscal value. Who authorized a discount isn't printed — it's still recorded (`discount_authorized_by_user_id`) for audit, just not on the customer-facing receipt. `sale.created_at` is stored in UTC (SQLite's `datetime('now')`) but printed converted to local time (`fmt_local_datetime`), matching the frontend's `fmtDateTime` — otherwise the PDF and the on-screen preview would show different hours.

## Dashboard (`commands/dashboard_layout.rs`, `commands/dashboard.rs`)

Admin-only screen — every command here calls `require_admin`, never just `active_user_id`.

| Command | Signature | Notes |
|---|---|---|
| `get_dashboard_layout` | `() -> Vec<DashboardLayoutItem>` | the logged-in Admin's own layout — resolved from `AppState.active_user_id`, no `userId` argument (see `CLAUDE.md`'s Auth rule). Seeds `db::DEFAULT_DASHBOARD_LAYOUT` the first time this Admin's layout is empty, instead of an empty grid |
| `save_dashboard_layout` | `(items: Vec<DashboardLayoutItem>) -> ()` | replaces the logged-in Admin's entire layout in one transaction (delete + re-insert). Called on every drag/resize (debounced client-side, 500ms) and on every add/remove-card click (immediate — no debounce, so closing the app right after doesn't lose the change) |
| `get_dashboard_data` | `() -> DashboardData` | one aggregate round-trip for every card — cards never fetch their own data (`src/components/dashboard-cards/*`, each a "dumb" component reading its own slice of `DashboardData` via props). All money/count figures scoped to "hoje"/"mês atual" use local time both in SQL (`'localtime'` modifier) and Rust (`chrono::Local`), matching how the rest of the app converts the UTC `created_at` columns for display. Every sales/revenue figure excludes `status = 'cancelled'` (a cancelled sale's `sale_payments` row is never deleted, so an unfiltered sum would double-count money that was actually reversed) — decided after the fact, since Cancelamento/Estorno was designed after the Dashboard's original card list. `discountGrantedMonth` uses the same "gross minus total" formula as `list_sales`'s `discountValue` (see above), aggregated for the month. `lowStockCount`/`lowStockItems` reuse `commands::config::low_stock_percent` and the same "critical or warning" threshold formula as `lowStockWarningThreshold` in `src/lib/api.ts` (not just `quantity <= min_quantity`) — otherwise the Dashboard would undercount relative to Estoque's own yellow "Baixo" chip, which already covers that wider band. `creditOutstandingTotal` reuses `commands::clients::client_balance` per client (same aggregate Clientes' own "Total em aberto" stat is built from) rather than a separate SQL formula, so the two can't drift apart. `remindersDue` mirrors `ClientsPage.tsx`'s `ReminderBadge` window (`REMINDER_WARNING_DAYS = 7`, hand-kept in sync — no shared Rust/TS date-rules module yet) and only includes clients with an open balance |

## Backup (`commands/backup.rs`)

`backup_folder` is a single global `config` row (not per-user): whichever Admin sets it applies to the whole app.

| Command | Signature | Notes |
|---|---|---|
| `get_backup_folder` | `() -> Option<String>` | admin-only (unlike most `config` getters, which any logged-in profile can read) — the entire Backup section of Configurações is invisible to Usuário comum, not just its restore button |
| `set_backup_folder` | `(path) -> ()` | admin-only. No validation that `path` is writable — a bad folder only surfaces as a `run_backup` failure toast later |
| `clear_backup_folder` | `() -> ()` | admin-only. Deletes the `config` row outright (not set to empty string) — `run_backup` treats a missing row as "backup disabled", same convention `get_backup_folder` returning `None` reads |
| `run_backup` | `() -> ()` | **not** admin-gated (only `active_user_id`) — called by `AppShell` regardless of which profile is logged in, once on mount and then every 10 minutes for as long as the app stays open. A no-op when no folder is configured. Writes `<folder>/stockly-backup.db` — fixed filename, overwritten each run, no version history — via `VACUUM INTO`, not a raw `std::fs::copy`: a raw copy can be inconsistent with an active WAL-mode connection (`-wal`/`-shm` files not reflected in a plain copy), while `VACUUM INTO` is SQLite's own way to snapshot the open database consistently. Removes any existing file at the destination first, since `VACUUM INTO` refuses to overwrite one |
| `import_backup` | `(path) -> ()` | admin-only. Validates `path` opens as SQLite and has a `users` table before touching anything (rejects a random `.db` file). Swaps `AppState.db` for an in-memory connection, then `std::fs::copy`s `path` over the live database file — the app is expected to call `relaunch()` (`@tauri-apps/plugin-process`) right after, to reopen the imported file fresh. The frontend (`RestoreBackupModal`) adds its own re-confirmation step (the admin's own password, re-verified via `verify_password`) before ever calling this — already Admin-only, but destructive enough (overwrites the *entire* active database) to also guard against an accidental click |
