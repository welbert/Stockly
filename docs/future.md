# Future ideas / known gaps

Things noticed along the way that aren't part of the current implementation scope. This file is what's left of `Plans/PLANO.md` (the original product/business-rules spec) and `Plans/mockups-*.html` — those have been removed now that everything in them is built; this is where anything still-open from that spec lives on.

## Estoque / Relatórios

- **Stock-rupture forecast** — instead of just comparing current quantity to a fixed minimum, compute each item's average daily sales over a recent window (e.g. last 90 days of `sale`-type `stock_movements` rows) and project days remaining: `dias_restantes = quantidade_atual ÷ (soma das saídas no período ÷ dias do período)`. Could show as an extra status badge in Estoque ("Tendência: acaba em ~N dias") in addition to a dedicated "Sugestões" screen. The ledger needed for this (`stock_movements`) is already recorded from day one specifically so this doesn't need retroactive data once built.
- **Price/margin-over-time report** — "no dia X este item custava Y" or a chart of margin (`sale_price - cost_price`) drifting over time. The ledger needed (`item_price_history`) is already recorded from the moment `update_item` first changes a price, same reasoning as `stock_movements` above — no consultation screen yet, this is purely the data source waiting for one.

## Crediário / Clientes

- **Manual debt increase (e.g. interest for a long-overdue balance)** — today `client_balance` is purely derived (completed Crediário sales minus active `credit_payments`); there's no way to add debt to a client outside of an actual sale. A real feature, not a small tweak:
  - New table, same shape as `credit_payments` (soft-cancel: `cancelled_at`/`cancelled_by_user_id`/`cancel_authorized_by_user_id`/`cancel_reason`) — a wrongly-applied charge needs the same reversal trail as a wrongly-registered payment.
  - `client_balance` (and everything built on it — Clientes, the Dashboard's `credito_em_aberto` card, `has_open_debtors`) would need to add this new table into the sum alongside sales and payments.
  - Unlike registering a payment (no admin password required today, since it only *reduces* debt), this *increases* what a client owes — likely needs to be Admin-only or go through `resolve_admin_authorization`, not left as self-service.
  - The real scope-deciding question is business rules, not schema: is this a flat amount an Admin types in by hand each time, or should the app calculate interest automatically (a rate, whether it accrues per overdue sale or against the total balance, and when it runs — on every app open? a periodic job?)? Manual entry is the scope above; automatic calculation is substantially bigger and nothing like it exists elsewhere in the app yet.

## Impressão / Recibo

- **Physical printing path for the Tomate MDK-082 thermal printer — genuinely open, can only be resolved with the hardware in hand.** It was already decided the receipt PDF (`genpdf`) renders at **80mm continuous-roll width** (implemented), but which of two very different printing paths actually works depends on whatever driver ships with this printer, which its product page doesn't confirm:
  1. **Regular printing** — installs as a normal Windows printer (GDI driver), sends the PDF to the Windows spooler. Works as long as the driver is configured for 80mm continuous roll, not fixed-page paper.
  2. **Raw ESC/POS** — bypasses the graphical driver and sends commands straight to the printer (auto-cut, bold, opening a cash drawer if present) — common on "real" POS hardware, but a **different pipeline** from "generate a PDF and print it" (the `genpdf` PDF would still serve the digital save/open case, but physical printing wouldn't reuse it on this path).
  - Cheap thermal printers sold this way in Brazil typically ship with either a "generic/text" driver (bad at printing PDF/graphics correctly) or a real ESC/POS-compatible one — only testing with the hardware (or reading the manual/driver docs) confirms which one the MDK-082 is.
  - Until tested, the flow stays "generate the PDF and open/save/print via the shell's `print` verb" (`SalesPage`/`SalesHistoryPage`'s "Imprimir" button, already implemented).
  - **Plan B if the shell `print` verb proves inconsistent in real testing**: bundle **SumatraPDF** (a lightweight, free PDF reader) and use `SumatraPDF.exe -print-dialog recibo.pdf`, which always opens the native Windows print dialog regardless of the user's default PDF reader — costs ~10MB more in the Tauri installer. Only worth migrating to if the v1 shell-verb approach shows up as unreliable in practice, not preemptively.

## Auditoria

- **`audit_log` now exists** (`db.rs`/`docs/database.md`) — an append-only table covering desconto concedido, venda cancelada, pagamento de Crediário cancelado, and senha redefinida, backfilled once from the 3 sources that predate it and fed by `commands::audit::record`, called inline from each action's own command. The two ideas below predate that table and are lighter to do now that it exists.
- **Client-rename authorization isn't persisted** — `commands::clients::update_client` calls `resolve_admin_authorization` when renaming a client with an open balance, but discards the result (never writes who authorized it or when). This is why "Autorizações de Administrador" (`relatorios/autorizacoes-admin`) still doesn't cover cliente renomeado, even though `audit_log` itself is no longer the blocker (it was, before this table existed — a plain pair of columns on `clients`, a current-state table, would only ever hold the *last* rename, silently dropping every earlier one). Now it's just a 4th `commands::audit::record` call inside `update_client`'s already-existing authorized-rename path, `client_id` set, no new table needed.
- **Broader audit log of admin actions** — `audit_log` currently only covers the 4 action types above; who created/edited/deactivated a user (`create_user`/`update_user`/`delete_user`, none of which call `commands::audit::record` today) isn't logged, and neither is anything outside "an action that needed admin authorization" (e.g. editing an item's price/quantity — already covered by `item_price_history`/`stock_movements`, separate ledgers with their own consultation screens). Would be more `record` calls plus new `action_type` values, not a schema change.
- **Retention with export-before-delete, if `audit_log` ever needs pruning** — SQLite has no built-in TTL/expiry feature (unlike DynamoDB), so this would always be a manual `DELETE ... WHERE created_at <= ...` run periodically (e.g. piggybacking on the existing 10-minute backup timer). Decided against doing this reflexively though: at this app's single-store scale, the table isn't likely to become a real size/performance problem within a year or two, and an audit trail's whole purpose is answering "who did what, when" — sometimes long after the fact — so silently deleting old rows works against that. If pruning is ever needed (disk space, a retention policy, LGPD), export the rows being deleted to a file first (CSV, next to backups) rather than just discarding them — keeps the data reachable without the live table growing forever.
