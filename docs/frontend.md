# Frontend

## Routing (`src/App.tsx`)

```
AuthGate                                    (src/components/layout/AuthGate.tsx)
├── no session  → renders <LoginPage/> directly (not a nested route)
└── session ok  → <Outlet context={{ secondsUntilLock }}/> → AppShell
                      ├── index ("/")        → HomeRedirect (Admin → "/dashboard", Usuário comum → "/venda")
                      ├── "dashboard"        → DashboardPage (Admin-only; self-redirects to "/" otherwise)
                      ├── "venda"            → SalesPage (Venda/PDV)
                      ├── "estoque"          → InventoryPage (Estoque)
                      ├── "devedores"        → DevedoresPage (Crediário)
                      ├── "historico"        → SalesHistoryPage (Histórico de vendas)
                      ├── "relatorios/vendas-periodo"        → VendasPorPeriodoPage (Admin-only; see "Relatórios" below)
                      ├── "relatorios/vendas-categoria-item" → VendasPorCategoriaItemPage (Admin-only)
                      ├── "relatorios/vendas-forma-pagamento"→ VendasPorFormaPagamentoPage (Admin-only)
                      ├── "relatorios/vendas-operador"       → VendasPorOperadorPage (Admin-only)
                      ├── "relatorios/comparativo-periodos"  → VendasComparativoPeriodosPage (Admin-only)
                      ├── "relatorios/movimentacao-estoque"  → MovimentacaoEstoquePage (Admin-only)
                      ├── "relatorios/historico-preco"       → HistoricoPrecoPage (Admin-only)
                      ├── "relatorios/itens-parados"         → ItensParadosPage (Admin-only)
                      ├── "relatorios/:slug"                 → ReportPlaceholderPage (every other report — Admin-only)
                      ├── "configuracoes"    → SettingsPage
                      └── "usuarios"         → UsersPage (Admin-only; self-redirects to "/" otherwise)
```

`HomeRedirect` (`App.tsx`) is the only thing ever mounted at "/" — `DashboardPage`/`UsersPage`'s own "not allowed" fallback (`<Navigate to="/" replace />`) and the catch-all route both bounce through it too, landing on the correct per-role screen instead of hardcoding "/venda" themselves.

`AuthGate` owns the single `useIdleTimer` call for the whole app and passes `secondsUntilLock` down to `AppShell`'s topbar warning via React Router's `<Outlet context={...}>` / `useOutletContext<AuthGateOutletContext>()` — a plain exported interface, not a React Context module, since it's one value flowing to one child route subtree (`AppShell`) rather than something read from many unrelated places.

## Pages (`src/pages/`)

- **LoginPage** — branches on `hasAnyUsers()`: first-run shows an admin-creation form (`FirstRunForm`); otherwise a keyboard-navigable profile picker (`ProfilePicker`, arrow keys + Enter) followed by a password step.
- **InventoryPage** (Estoque, `"estoque"` route — not the landing screen, see `HomeRedirect` above) — search (accent-insensitive, `\p{Mn}` NFD strip via `normalize()` in `lib/format.ts`) + category filter, computed client-side over `list_items()`'s full result (no server-side filtering). Row actions differ by role: Admin gets "Editar"/"Excluir" (`ItemFormModal`), Usuário comum gets "Ajustar estoque" (`StockAdjustModal`) and only for active items — both also reachable via right-click (`ContextMenu`, see below). Paged client-side via the shared `Pagination` component (see below), page resets to 0 whenever the search term or category filter changes.
- **DashboardPage** (Admin-only) — see its own section below.
- **SalesPage** (Venda/PDV) — see its own section below.
- **DevedoresPage** (Crediário, both roles — see `CLAUDE.md`'s note under "Planning source of truth" about screens the Usuário comum mockup doesn't duplicate) — see its own section below.
- **SalesHistoryPage** (Histórico de vendas, both roles) — see its own section below.
- **SettingsPage** — `Card` per concern: Aparência (`ThemeSwitcher`), Bloqueio automático (auto-lock dropdown, self-service for both roles), Diagnóstico (both roles too — "Abrir pasta de logs" via `open_log_dir`; `Plans/PLANO.md` lists it without the "exclusivo do Administrador" qualifier the other Configurações items get), and four Admin-only cards (Alerta de estoque baixo %, Precificação — default profit margin %, Crediário — on/off checkbox, blocked server-side while any client has an open balance, and Recibo — store name + free-text info lines for the receipt header, plus the footer's thank-you message; all saved on blur rather than per keystroke, the Crediário checkbox on change).
- **UsersPage** — Admin-only table + `UserFormModal`; guards itself with `if (!user?.isAdmin) return <Navigate to="/" replace/>` since it's still reachable by URL even though the sidebar hides the link.
- **ReportPlaceholderPage** (`relatorios/:slug`, Admin-only) — reads `slug` from the URL and looks it up in `lib/reportsCatalog.ts`; redirects to "/" when the slug isn't in the catalog or the profile isn't Admin, same guard shape as `UsersPage`. Still renders the plain "não implementado ainda" placeholder for every report except the three below — each remaining one gets real content later by giving it its own literal route in `App.tsx` (ahead of the catch-all `"relatorios/:slug"`) and a component, same as these did, without touching navigation again.
- **`usePeriodFilter`/`PeriodToolbar`** (`src/pages/reports/`) — the "Últimos 7 dias / Este mês / Personalizado" period picker every Vendas report shares (`Plans/mockups-relatorios.html`'s toolbar `<select>`), extracted once three reports needed the exact same state/range logic. `usePeriodFilter()` owns `preset`/`customFrom`/`customTo` state and derives `range`/`periodLabel`; `PeriodToolbar` renders the `<select>` + resolved-range label (hidden for "Personalizado", whose De/Até inputs already show the dates) + `children` (export buttons, a variant switch, ...) after a flex spacer. A new report wires both instead of copy-pasting the toolbar again.
- **VendasPorPeriodoPage** (`src/pages/reports/`, `relatorios/vendas-periodo`, Admin-only) — the first real Relatórios screen, establishing the pattern the rest of the catalog follows: the shared period toolbar (see `usePeriodFilter`/`PeriodToolbar` above), 4 stat cards, a daily bar chart (same `Bar`/Chart.js setup as the Dashboard's `VendasPorPeriodoCard`, just not tied to a fixed 7 days), and — the one addition beyond the mockup, deliberately — a **raw sales listing right below the chart**, paginated the same way as `SalesHistoryPage`. The listing exists so the numbers above are traceable back to the sales that produced them, and so "Exportar CSV"/"Exportar PDF" have real rows to export instead of just aggregates (`toSaleCsvRows`/`exportSalesCsv`/`exportSalesReportPdf` in `lib/api.ts` — the CSV button is shared verbatim with `SalesHistoryPage`'s own; see `docs/commands.md`'s `export_sales_report_pdf` for why the PDF deliberately doesn't reproduce the chart). Computed entirely client-side over `listSales()` (same "fetch everything, filter/aggregate in the component" convention as Estoque/Histórico, no dedicated backend command for the report *data* — only the export writes go through the backend) — only `status === "completed"` sales count, matching the Dashboard's own exclusion of cancelled sales from every money/count figure, so the listing's rows always sum to the totals shown above them. Ticket médio has an `InfoTooltip` explaining the formula; Dia de pico shows the actual date under the weekday abbreviation (and inline in the PDF, which has no hover/secondary line) so a month-long period doesn't leave "Ter" ambiguous between four different Tuesdays.
- **VendasPorCategoriaItemPage** (`relatorios/vendas-categoria-item`, Admin-only) — the shared period toolbar plus a "Por categoria"/"Por item" pill switch (same visual pattern as `ThemeSwitcher`, kept inline here rather than extracted — only two static options, unlike `ThemeSwitcher`'s catalog-driven set). "Por categoria" is a donut + legend/table (categoria, % do total, total); "Por item" is a table sorted by quantity vendida (categoria, qtd., total) — same two mockup panels, one toggle. Needs `listSaleItemsReport()` (line-item-level, unlike `listSales()`) since a category/item breakdown needs each `sale_items` row, not just each sale's total; grouped client-side by `categoryName ?? "Categoria indefinida"` (categoria) or `itemName` (item, matching `commands::dashboard::top_selling_items`'s own `GROUP BY si.item_name`). Exports whichever variant is currently showing via the generic `exportReportCsv`/`exportReportPdf` (not `exportSalesCsv`, since neither variant's row shape is a per-sale `SaleCsvRow`).
- **VendasPorFormaPagamentoPage** (`relatorios/vendas-forma-pagamento`, Admin-only) — the shared period toolbar, a donut (by **count**, not R$, matching the Dashboard's `FormasPagamentoCard` and its fixed per-method `colorFor` — a method should always read the same color) with a centered vendas count, and a Forma de pagamento/Nº de vendas/Total table beneath doubling as the export source. Computed client-side over `listSales()` (has `paymentMethod` already, no new backend data needed) via the same generic `exportReportCsv`/`exportReportPdf`.
- **VendasPorOperadorPage** (`relatorios/vendas-operador`, Admin-only) — the simplest Relatórios screen so far: just the shared period toolbar and an Operador/Nº de vendas/Total vendido/Ticket médio table (`Plans/mockups-relatorios.html` has no chart for this one either), sorted by total vendido descending. Same `listSales()`-only data source as Forma de pagamento (`userName`/`total` already there) and the same generic `exportReportCsv`/`exportReportPdf`.
- **VendasComparativoPeriodosPage** (`relatorios/comparativo-periodos`, Admin-only) — added to the catalog after the original 11-report scope, on request (comparing one month against any other, not just "vs. mês anterior", was judged useful enough to add outright). Doesn't use `usePeriodFilter`/`PeriodToolbar` — the comparison unit is a whole calendar month picked from **two** dropdowns, not a 7d/mês/personalizado range. Both dropdowns only list `availableMonths`: the distinct `YYYY-MM` values with at least one completed sale (derived from `listSales()`, sorted newest first) — so there's never an empty month to pick, per the explicit ask. Defaults to the two most recent available months (or the same month twice if only one exists). Variação (`%`) is `null`/shown as "—" when the comparison month's value is `0` (an "infinite%" change from zero isn't a meaningful number). Exports the "Detalhamento" table (Métrica/mês A/mês B/Variação) via the generic `exportReportCsv`/`exportReportPdf`.
- **MovimentacaoEstoquePage** (`relatorios/movimentacao-estoque`, Admin-only) — the `stock_movements` "tela de consulta" `docs/database.md` had registered as pending since the table was created. The shared period toolbar plus an `ItemFilterCombobox`/tipo `<select>` (with a "Limpar filtro" button, shown only once either is set), over `listStockMovements()`. Tipo badge colors mirror the mockup (Venda=info, Entrada=success, Ajuste=warning, Estorno=danger, Inicial/Importação CSV=neutral — the last one didn't exist when the mockup was drawn, added since CSV import started logging `csv_import` movements). Beyond the mockup: a "Qtd. total" column, the running balance for that item right after this movement (`runningTotalByMovementId` — grouped by `itemId`, summed in `id` order over the movement, not `createdAt` string order, since same-second ties can't be trusted to sort right), always computed from the full, **unfiltered** `movements` — narrowing by período/tipo/item only changes which rows are visible, never what this column reads for the rows that stay.
- **HistoricoPrecoPage** (`relatorios/historico-preco`, Admin-only) — `item_price_history` timeline, no period filter (it's an audit trail, not naturally date-scoped like sales). "Todos os itens" (default) is a flat table with an "Item" column; picking one item drops that column and turns the `Card` title into the item's name, matching the mockup's focused view. The earliest row per item (`create_item` always writes one on creation) shows "cadastro do item" in place of the operator's name — it's a snapshot, not a real price change. Filtered to one item, each Custo/Venda cell also gets a `▲`/`▼` (`PriceCell`) against the previous (chronologically older) record for that same item — computed from the full `filtered` array before pagination (`rowsWithDelta`, `filtered[i + 1]` since the data is newest-first), so a row at the top of a page still compares correctly against the last row of the page before it. Only shown in single-item mode — in "Todos os itens", consecutive rows can belong to different items, so comparing them wouldn't mean anything.
- **ItensParadosPage** (`relatorios/itens-parados`, Admin-only) — a threshold `<select>` (30+/60+ dias, the only two the mockup offers) instead of the shared period toolbar. Reuses `listStockMovements()` (filtered to `movementType === "sale"`, grouped by `itemId` for each active item's most recent sale) rather than a dedicated backend query. An item that's never sold at all always shows (`"nunca vendido"` badge, days-parado treated as `Infinity` so it sorts to the top), regardless of which threshold is picked.

## Relatórios (`src/lib/reportsCatalog.ts`, `AppShell`'s nav tree)

`Plans/PLANO.md`'s "Menu lateral expansível": "Relatórios" in the sidebar never navigates directly — it expands in place, same as the `Plans/mockups-relatorios.html` mockup, except taken one level further: the mockup's "Vendas"/"Estoque"/"Crediário / Devedores"/"Auditoria" are static section labels inside one flat expanded list, but here they're their own expandable groups (nested inside "Relatórios"), added deliberately as a second level to validate the mechanism generalizes — any future menu that needs sub-screens (a "Cadastros" group, say) reuses the same pieces instead of a bespoke toggle.

- **`reportsCatalog.ts`** is the single source of truth: `REPORT_GROUPS` (id, label, and each group's `ReportDef[]` — slug/label/subtitle) feeds `AppShell`'s nav tree, `App.tsx`'s single `"relatorios/:slug"` route, and `ReportPlaceholderPage`'s header/body text. Adding a report is one entry here, not three places kept in sync by hand. **Scope decided with the product owner**: 12 reports in the catalog (Vendas por período/categoria-item/forma de pagamento/operador, Comparativo de períodos; Movimentação de estoque, Histórico de alteração de preço, Itens sem movimento; Inadimplência aging, Pagamentos recebidos, Pagamentos cancelados; Autorizações de Administrador) — every one of them has its own route/component now (see `Plans/PLANO.md`'s "Candidatos a relatório") **except** "Autorizações de Administrador", still a blank `ReportPlaceholderPage`. The rest of `PLANO.md`'s "Candidatos a relatório" list (Ticket médio, Descontos concedidos, Vendas canceladas, Margem/lucro, Estoque valorizado, Previsão de ruptura) is intentionally left out of the menu until prioritized.
- **`NavItemRenderer`** (in `AppShell.tsx`, not its own file yet — nothing outside `AppShell` needs it so far) is the generic, recursive piece: a `NavItem` is either a `{ kind: "link" }` leaf (a `NavLink`) or a `{ kind: "group" }` node (a toggle button + its own `children: NavItem[]`, rendered at `depth + 1`) — nesting works to any depth, not just the two levels Relatórios happens to use. Defined at **module scope**, not inside `AppShell`, on purpose: an inline component gets a new identity every `AppShell` render (e.g. every idle-timer tick), which would remount the whole tree and silently collapse every open group each render.
- **Open/closed state**: a group defaults open when it contains the currently active route (`containsPath`, recursive) — so navigating straight to a report (not via a click, e.g. a fresh page load) still shows it correctly nested under its groups. `AppShell.manualOpen` (`Record<groupId, boolean>`) only overrides that default once the admin actually clicks a group's toggle; it's read as `manualOpen[id] ?? defaultOpen`, not a plain boolean default, precisely so a manual collapse of a group that contains the active route is respected instead of snapping back open on the next render.
- **`REPORTS_NAV_GROUP`** (`AppShell.tsx`) is built once from `REPORT_GROUPS`, wiring group ids as `relatorios-<groupId>` and leaf `to` as `reportPath(slug)` — the whole "Relatórios" entry is a single `adminOnly: true` row in `NAV_ITEMS`, same admin gating as `Dashboard`/`Usuários`, so it (and everything nested inside it) never renders for Usuário comum.

## Dashboard (`src/pages/DashboardPage.tsx`, `src/components/dashboard-cards/`)

Admin-only (`Plans/PLANO.md`'s "Dashboard"), same architecture as the sibling CashVault project's own customizable dashboard: a draggable/resizable card grid backed by a catalog, instead of a fixed layout.

- **Data**: `DashboardPage` fetches `getDashboardData()` once on mount (one aggregate round-trip, `commands::dashboard::get_dashboard_data` — see `docs/commands.md`) and hands the whole `DashboardData` object down as `cardProps={{ data }}` to `DashboardGrid`. No card fetches its own data — each is a "dumb" component that only reads its own slice of `data` via props, which is what lets a card be added/removed from the catalog without touching any fetch logic.
- **Grid** (`DashboardGrid.tsx`) — built on `react-grid-layout` v2's `GridLayout` component (`gridConfig`/`dragConfig`/`resizeConfig`/`constraints` props, `LayoutItem[]` layout), `GRID_COLS = 6` columns, `ROW_HEIGHT = 180`px rows. **Screen-size delimiter**: `useContainerWidth()` (from the same library) measures the actual available width via `ResizeObserver` and feeds it straight into `GridLayout`'s `width` prop — the grid, and therefore every card's pixel size, is always bounded to what actually fits the window, never wider. In edit mode a dashed outline wraps the grid at that exact measured width (not the full screen), so it's visually clear where the editable area ends even when there's empty space to the right on a wide monitor. `visibleItems` and each item's resize `constraints` are memoized/precomputed (`CARD_CONSTRAINTS`, built once at module scope from the static `CARD_CATALOG`) rather than rebuilt inline in the `layout` `useMemo` on every render — `react-grid-layout` deep-compares its `layout` prop with `fast-equals`, which treats functions by reference; a fresh `allowedSizeConstraint(...)` closure every render made every recompute look "different" even with identical x/y/w/h, which made the library treat it as an external layout change, fire `onLayoutChange`, update this component's own state, and recompute again — forever ("Maximum update depth exceeded", pegged the CPU while the Dashboard was open). The sibling CashVault project had the exact same bug (this architecture was ported from there) and got the same fix.
- **Catalog** (`catalog.ts`) — `CARD_CATALOG: Record<CardKey, { label, description, allowedSizes, component }>`. `description` feeds both the "?" tooltip that `DashboardGrid` overlays on every card and the text shown in "+ Adicionar card" — no card renders its own explanation. `allowedSizes` reflects the real shape of each card's content (a stat is always compact `1x1`/`2x1`; a donut is narrow-and-tall, never full width; a table/list gets extra height options; the 7-day trend chart wants width) — resizing always **snaps** to the closest allowed size (`gridConstraints.ts`'s `allowedSizeConstraint`/`sizeFromDimensions`), never a free per-pixel resize. 18 cards total; see the table below.
- **Default layout** (`db::DEFAULT_DASHBOARD_LAYOUT`, backend) — only 8 of the 18 catalog cards ship visible the first time an Admin opens the screen (six 1x1 stats filling the first row exactly, then the low-stock table and the sales trend chart sharing the row below), so a fresh dashboard isn't overwhelming. The other 10 exist in the catalog and stay opt-in via "+ Adicionar card". Each Admin has their **own** layout (`dashboard_layout.user_id`, see `docs/database.md`) — one Admin customizing their dashboard never touches another's.
- **Edit mode** (`useDashboardLayout.ts`) — "✎ Personalizar" toggles `dragConfig.enabled`/`resizeConfig.enabled` and reveals "+ Adicionar card" (opens `AddCardDrawer`, listing catalog entries not currently visible — stays open after each pick, same "add several in a row" reasoning as Venda's `StockBrowserModal`) and a per-card "✕" (sets that card `visible: false`, still re-addable later — never actually deleted from the row until replaced by a fresh default). Re-adding a previously-removed card is repositioned to the current bottom of the layout (`x: 0, y: maxY`, recomputed fresh), not restored to whatever `x`/`y` it had before removal — otherwise it could reappear on top of a card the user rearranged into that spot in the meantime; its old `size` is kept, just not the stale position. Drag/resize autosaves debounced (500ms, `persistDebounced` — `onLayoutChange` fires many times a second mid-gesture, saving on every one would hammer the DB for nothing); add/remove-card saves immediately (`persistImmediate` — debouncing a discrete click would risk losing it if the app closes in that window). Every outgoing save is chained after the previous one settles (`saveChain`, a running promise) rather than fired independently — two saves triggered close together (e.g. adding two cards back to back) are two separate Tauri IPC round-trips with no inherent ordering guarantee, so without this the older (smaller) list could land in the DB *after* the newer one and silently overwrite it; the lost card would only resurface as "addable again" on the next reload. **Undo** ("✕ Cancelar"): a snapshot of the layout is taken the moment edit mode is entered (`snapshotRef`); "✓ Concluir" just flushes any pending debounced save, but "✕ Cancelar" restores and re-saves that snapshot, discarding everything autosaved during the whole editing session — not just the last drag. **Help** ("Clique aqui para ajuda", only shown in edit mode) opens `DashboardHelpModal` — three small looping CSS animations (hand-built, not a real recording, same idea as `KeyboardShortcutsModal`'s keyboard diagram) illustrating add/move/resize for whoever doesn't find the buttons/corner handle self-explanatory on the first visit.
- **Cards** (one file each, `src/components/dashboard-cards/`) — most render through the shared `StatCard` (label + big value, ~10 near-identical cards); the rest are their own thing:

  | Card key | Shows |
  |---|---|
  | `itens_em_estoque` | Total quantity in stock (active items) |
  | `valor_em_estoque` | Stock value at **cost** (`cost_price × quantity`), not sale price — see `Plans/PLANO.md` |
  | `vendas_hoje` / `vendas_mes` | Total sold today / this month (completed only) |
  | `recebidos_hoje` / `recebidos_mes` | Cash/Card/PIX + Crediário settlements actually received — differs from "Vendas" because a Crediário sale counts as a sale before the money comes in |
  | `estoque_baixo` | Count of items at/under their minimum quantity |
  | `itens_estoque_baixo` | Table of those items, most critical first |
  | `vendas_por_periodo` | Bar chart, last 7 days (Chart.js) |
  | `vendas_por_categoria` | Donut, this month's sales by category (Chart.js) |
  | `top_itens_vendidos` | Table, top-selling items this month by quantity |
  | `formas_pagamento` | Donut, this month's sale count by payment method (Chart.js) |
  | `ultimas_vendas` | List of the most recent completed sales |
  | `comparativo_mensal` | % change vs. the previous month (`null` shown as "—" when there's nothing to compare against) |
  | `devedores_lembrete` | Clients with an open balance and a reminder due/overdue (same window as Devedores' `ReminderBadge`) |
  | `credito_em_aberto` | Sum of every client's open Crediário balance — same figure as Devedores' own "Total em aberto" |
  | `descontos_concedidos` | Sum of item + general discounts granted this month |
  | `vendas_canceladas` | Count and total value of sales cancelled/estornadas this month |

- **Charts** use Chart.js + `react-chartjs-2` (first real usage in this app — `CLAUDE.md`'s stack table listed it from day one). Canvas can't take a `var(--color-primary)` string directly, so chart colors go through `themeColor()` (`src/theme.ts`), which reads the already-resolved CSS custom property via `getComputedStyle` — same trick the sibling CashVault project uses for its own charts.

## Venda / PDV (`src/pages/SalesPage.tsx`)

Keyboard-first by design — the item search input keeps `autoFocus` and gets refocused after every add/close so a cashier never needs the mouse for the common path:

- **Item search**: typing filters `list_items()`'s already-loaded result client-side (same `normalize()` as Estoque). Suggestions rank "name/code starts with" above "name/code contains anywhere", capped at 8, each showing available stock (a red "Sem estoque" chip blocks adding a zero-stock item, same rule/wording as `StockBadge`'s critical state). Pressing Enter first checks for an exact code match (adds it directly even if not the top suggestion), otherwise adds whichever suggestion is highlighted.
- **Shortcuts** (single `window` `keydown` listener, all disabled while any modal is open): `Enter` add item, `↑`/`↓` navigate the suggestion list (while one is open) or the cart rows (once search is empty), `+`/`-` adjust the selected row's quantity, `Delete` remove the selected row, `Esc` deselect the current row, `F6` open the discount modal (item-level if a row is selected, otherwise the order-level discount), `F2` open the finalize/payment modal, `F4` open the cancel-sale confirmation. Focus returns to the search input automatically whenever the last open modal closes (a single `useEffect` keyed on a `modalOpen` boolean, rather than an explicit `.focus()` call in every individual close handler). The cart's quantity cell also has mouse-clickable `-`/`+` buttons calling the same `adjustQuantity` the keyboard shortcut uses (`+` disabled once `quantity === line.available`) — added after real usage showed the keyboard-only shortcut wasn't discoverable enough on its own.
- **Estoque browser** (`StockBrowserModal`, opened via the "Estoque" button next to "Adicionar") — lets the cashier browse/search the full active item list (same shape as Estoque's own table: código, nome, categoria, preço, `StockBadge`) and add straight from it, for when a shopper wants to see what's available rather than search by exact code/name. Stays open after each pick (`onSelect` is `addItemToCart` itself, not wrapped) so several items can be added in a row; shares its error feedback with the main search box's `addError` state rather than keeping a separate one.
- **Client-side totals are a preview only** — `lineSubtotal`/`subtotal`/`total` in `SalesPage` mirror the backend's `round2` sequential math (item discount, then order discount) exactly, but the number that's actually charged and printed always comes back from `create_sale`'s response (`SaleDetail`), never something computed client-side.
- **Store name/info/thank-you message** (`getStoreName`/`getStoreInfo`/`getReceiptThankYouMessage`) are fetched once on mount and shown in place of the previously-hardcoded "BORA VENDER"/"Obrigado pela preferência!" — the live cart preview shows the header (name/info) since payment method isn't known yet pre-finalize; `ReceiptResultModal` shows both header and footer once the sale is done. Mirrors exactly what `receipts.rs` puts on the actual PDF, so the on-screen preview never disagrees with what gets printed.
- **Discount authorization**: a non-Admin cashier is asked for admin authorization (`DiscountModal`, admin picker + password, pre-checked live via `verify_password` for fast feedback) on **every** discount, item or general, even after an earlier one in the same sale was already approved — one approval must never implicitly cover a later, possibly larger, discount the authorizing admin never saw. `SalesPage`'s `saleAuth` state only keeps the *most recent* authorizer, to stamp `create_sale`'s single `discount_authorized_by_user_id`/`discount_authorized_at` for the sale. An Admin cashier skips this entirely (`DiscountModal`'s `requiresAuth` prop is `false`), same as the backend's self-authorization path.
- **Finalize**: `PaymentModal` offers Dinheiro/Cartão/PIX, plus Crediário when `getCreditEnabled()` says it's on (Configurações' toggle). Picking Crediário reveals an inline client step *inside the same modal* — never leaves the sale in progress: search-by-name (`listClients()`'s full result filtered client-side, same `normalize()`/starts-with-before-contains ranking as the item search, capped at 5 suggestions), a "+ Adicionar novo cliente" row that swaps in a small quick-add form (name required, phone/lembrete/observação optional; saves via `createClient` and auto-selects the result), or a selected-client chip (name + current balance, "Trocar" to go back to search) once picked. Once a client is picked, an optional "Valor pago agora" (`MoneyInput`, capped at `total`) lets the customer settle part of the debt on the spot — shows a live "Saldo Crediário após esta venda" preview (the client's running balance, distinct from this sale's own "Valor devido" on the receipt, see below). Typing the full `total` doesn't clamp; it instead shows a warning ("escolha Dinheiro, Cartão ou PIX em vez de Crediário") and disables "Finalizar" (`creditPaidNowInvalid`) — paying it all off at once belongs to a different payment method, but the field lets the cashier type freely and explains why rather than silently blocking keystrokes. The backend re-validates the same `< total` rule regardless (`create_sale` rejects `credit_paid_now >= total`). The chosen value travels through `createSale`'s `creditPaidNow` param, recorded as a `credit_payments` row (linked via `sale_id`) in the same transaction as the sale. "Finalizar" stays disabled until a client is selected whenever the method is Crediário. On success, `ReceiptResultModal` (non-dismissible until "Nova venda") shows a receipt preview built from the real `SaleDetail` (including "Cliente: ..." and, when a down payment was made, "Valor pago agora"/"Valor devido" — same wording as the printed PDF, see `docs/commands.md`) and offers Imprimir/Abrir pasta de recibos, generating the PDF on demand via `regenerate_receipt_pdf` first if `receiptPdfPath` came back `null` (PDF generation failed right after the sale committed).

## Devedores (`src/pages/DevedoresPage.tsx`)

Both roles see this screen identically (no `user.isAdmin` branching anywhere in it) — none of its actions are on the "Ações sensíveis" list in `Plans/PLANO.md`.

- **List + detail, two columns**: left is every client with `balance > 0` (`listClients()`'s full result filtered/sorted client-side — same "fetch everything, filter in the component" convention as Estoque), searchable by name/phone; right is the selected client's full detail (`getClientDetail(id)`, fetched only once a row is clicked — the summary list doesn't carry the credit-sales/payments history, that's a separate round-trip on selection). A "Mostrar quitados" checkbox lifts the `balance > 0` filter for the list/search only — the stat cards (`totalOpen`/`overdueCount`/"Devedores ativos") always stay scoped to real open balances regardless of the checkbox. A settled client (`balance <= 0`) shows a green "Quitado" chip in place of the amount; selecting one still opens the same detail panel, so an operator/admin can look up when/by whom a debt was paid off ("Pagamentos registrados" already has date + operador per payment).
- **Sort options** (`reminder`/`name`/`balance`, client-side): `reminder` (the default) puts the soonest `reminderDate` first and clients without one last — matches "ordenável por Data de Lembrete (mais próxima primeiro)" in `Plans/PLANO.md`.
- **Reminder badge** (`ReminderBadge`): red "Vencido: dd/mm" once the date has passed, yellow "Lembrete: dd/mm" within the next `REMINDER_WARNING_DAYS` (7 — a v1 threshold, not specified in `Plans/PLANO.md`), plain text further out or absent. Same red/yellow/none shape as `StockBadge`, different data source.
- **Stat cards**: "Total em aberto" and "Devedores ativos" are aggregates over the same filtered-to-`balance > 0` list; "Lembretes vencidos" counts only those with a past `reminderDate`.
- **Pagamento vinculado a venda(s)**: each row of "Vendas em Crediário" with `remaining > 0` and `status === "completed"` has a checkbox (`selectedSaleIds`, a `Set<number>` of `saleId`, reset whenever a different client is selected); checking 1+ rows shows an action bar ("N vendas selecionadas · total R$ X" + "Pagar selecionada(s)") that opens `CreditPaymentModal` with exactly those sales. There's no more client-level "Registrar pagamento" button — every payment starts from selecting the sale(s) it covers. Each sale row also shows its own "Saldo restante" and a status badge (`CreditSaleStatusBadge`: green "Quitada", yellow "Em aberto"/"Parcialmente paga", red "Cancelada", derived from `remaining`/`paid`/`status`, no extra round-trip). "Ver venda" on a row opens `SaleDetailModal`, which can also cancel/estornar the sale from there (see "Histórico de vendas" below) — its `onCancelled` callback reloads both the left list and the right detail, since reversing a Crediário sale changes the client's balance. Saving any of the other modals reloads the same two.
- **"Pagamentos registrados"** now has a "Vendas relacionadas" column: one clickable chip per `CreditPaymentAllocationSummary` in that payment's `allocations` (recibo + valor aplicado), opening `SaleDetailModal` for that sale — same as "Ver venda" elsewhere.
- **Pagination**: both histories ("Vendas em Crediário" and "Pagamentos registrados") are paged client-side via the shared `Pagination` component, 5 rows at a time, most recent first (the backend already returns them newest-first, so it's a plain slice, no re-sorting) — added once a recurring client's history made both tables scroll on forever. Each has its own page counter, both reset to page 0 whenever a different client is selected (`useEffect` on `selectedId`); registering a new payment (`CreditPaymentModal`'s `onSaved`) also jumps `paymentsPage` back to 0 and clears `selectedSaleIds`, so the payment just added is actually visible instead of sitting off-screen on whatever page the operator had scrolled to. Sale selection isn't page-scoped — checking a row on page 1, then a row on page 2, keeps both selected.
- **Cancelar pagamento**: each non-cancelled row in "Pagamentos registrados" has a "Cancelar" action opening `CancelCreditPaymentModal` (motivo required; admin password required unless the logged-in user already is Admin — `requiresAuth={!user.isAdmin}`, same `admins` list/picker pattern as `DiscountModal`). Never deletes the row — a cancelled payment shows a struck-through amount and "Pagamento cancelado em {data} por X devido a Y" in place of the action, plus "(autorizado por Z)" when a different admin authorized it than who requested the cancellation (omitted when the same person did both, i.e. an Admin cancelling their own way — comparing `cancelAuthorizedByName` against `cancelledByName`).

### Relatórios de Crediário/Devedores (`src/pages/reports/`)

Backed by two new commands (`list_credit_sales`, `list_credit_payments` — see `docs/commands.md`), both global (all clients) versions of what `get_client_detail` already computes per-client, following the same "fetch everything, filter/aggregate client-side" convention as the Vendas/Estoque reports.

- **`InadimplenciaAgingPage`** (`relatorios/inadimplencia-aging`) — no period toolbar, a snapshot of debt *as of now* (same reasoning as `ItensParadosPage`). Groups `listCreditSales()`'s rows (already filtered to `status === 'completed'` server-side) by `clientId`, taking only `remaining > 0` ones: `balance` is their sum, `oldestOpenSale` their earliest `createdAt`. Days overdue is computed from that oldest open sale's date, **not** `reminder_date` — a deliberate decision (`PLANO.md` left both options open): a sale date always exists for any real debtor, while a reminder is optional and can be rescheduled without the underlying debt getting any younger. Buckets: 0–7/8–30/31+ dias, badge-colored neutral/warning/danger; a donut breaks down total R$ open per bucket, same shape as `VendasPorFormaPagamentoPage`'s donut. Table sorted worst-first (`daysOverdue` descending).
- **`PagamentosRecebidosPage`** (`relatorios/pagamentos-recebidos`) — period-filtered (`usePeriodFilter`/`PeriodToolbar`) over `listCreditPayments()`, keeping only `cancelledAt === null` rows within `range`, filtered by the payment's own `createdAt`. Stat cards: total recebido, nº de pagamentos, ticket médio.
- **`PagamentosCanceladosPage`** (`relatorios/pagamentos-cancelados`) — same source, opposite filter (`cancelledAt !== null`), but the period filters by **`cancelledAt`**, not the original payment's `createdAt` — this is an audit of "how many cancellations happened in this window", not "which period's payments got cancelled later". Shows cliente, valor, data original, data/autor do cancelamento, motivo.

All three export via the generic `exportReportCsv`/`exportReportPdf` and wire `useToast` for export success/error, same as every other report.

### Relatório de Auditoria (`src/pages/reports/AutorizacoesAdminPage.tsx`)

`relatorios/autorizacoes-admin` — the last report in the catalog. Backed by `listAdminAuthorizations()` (`commands::audit::list_admin_authorizations`, see `docs/commands.md`), which merges 3 sources (desconto concedido, venda cancelada, pagamento de Crediário cancelado) into one `AdminAuthorizationRow[]`, already sorted newest-first. Period-filtered (`usePeriodFilter`/`PeriodToolbar`) by `createdAt`, plus a `typeFilter` `<select>` ("Todos os tipos"/Desconto/Venda cancelada/Pagamento cancelado) rendered inside the toolbar, same slot/pattern as `MovimentacaoEstoquePage`'s movement-type filter. 4 stat cards (total + one count per type). Table columns: Tipo (color-coded badge per `actionType`), Referência (recibo — `—` for a payment cancellation, which has none), Cliente, Valor, Solicitado por, Autorizado por, Data — `requestedByName`/`authorizedByName` are the same name when an Admin self-authorized their own action (no separate password typed), shown as-is rather than specially collapsed, unlike `DevedoresPage`'s "(autorizado por Z)" convention. The 4th candidate source from `PLANO.md` ("cliente renomeado com saldo em aberto") isn't included — see `commands::audit::list_admin_authorizations`'s doc comment and `docs/future.md`'s "Auditoria" section for why.

## Histórico de vendas (`src/pages/SalesHistoryPage.tsx`)

Both roles see this screen identically — locating a sale to cancel/estornar is exactly the "Usuário comum can initiate, Admin authorizes" shape already used for discount, so the screen itself can't be Admin-only.

- **List + search**: `listSales()`'s full result (lightweight `SaleListItem` rows, no line items — those are a separate `get_sale_detail` round-trip once a sale is opened), filtered client-side by a single text box (recibo/cliente/operador, `normalize()`-matched), a De/Até date range (`localDateKey`, `lib/format.ts`, converts the UTC `createdAt` to a local `YYYY-MM-DD` for the comparison, same UTC→local conversion `fmtDateTime` does elsewhere — also reused by `VendasPorPeriodoPage` to bucket sales by day), and two `<select>` dropdowns (status: Concluída/Cancelada; forma de pagamento, options generated from `PAYMENT_METHOD_LABEL`'s keys so a new payment method never needs a second edit here) — same "fetch everything, filter in the component" convention as Estoque/Devedores. Paged client-side via the shared `Pagination` component (see below) with a 10/20/50 page-size `<select>` (default 20) — the only screen that exposes that choice, since it's the one whose table can realistically grow into the thousands; page resets to 0 whenever any filter changes. Besides "Total Final" (renamed from a plain "Total" once a discount column existed right next to it, for clarity), a "Desconto" column shows `s.discountValue` (`-R$ X,XX`, or "—" when `0` — see `docs/commands.md`'s `list_sales` entry for how that combined figure is computed). An "Exportar CSV" button (not in the original mockup, added since — same rationale as `VendasPorPeriodoPage`'s own listing: the data should be exportable, not just viewable) exports whatever's currently `filtered` (respecting every active filter above), via the same `toSaleCsvRows`/`exportSalesCsv` `VendasPorPeriodoPage` uses.
- **Row click** opens `SaleDetailModal` for that sale (same modal Devedores' "Ver venda" uses). A cancelled sale's row is dimmed (`opacity-60`), its total struck through, and a red "Cancelada" chip replaces the green "Concluída" one.
- **Row actions ("⋮")**: a per-row icon button (right-aligned, `stopPropagation` so it doesn't also trigger the row's own click-to-detail) opens a `ContextMenu` positioned at the click point — same component Estoque uses for right-click, just triggered by a left-click on a visible icon instead. Chosen over reusing the right-click convention because this is a POS app that may run on a touchscreen terminal, where right-click has no equivalent, and because a dense, small-screen-unfriendly table benefits from an explicit affordance over a hidden gesture. Its three actions: "Detalhe" (same as clicking the row), "Imprimir recibo", and "Abrir PDF do recibo" (`open_receipt_file`, opens the file directly, unlike `openReceiptsFolder` elsewhere) — the latter two call `regenerate_receipt_pdf` first (same "ensure it exists/is fresh" reasoning as `ReceiptResultModal`'s `ensurePdf`), surfacing a failure (e.g. the PDF file still open in another program, locked on Windows) as a dismissable line above the table (`actionError`).
- **Cancelar/Estornar**: `SaleDetailModal`'s "Cancelar / estornar venda" button (only shown while `status === "completed"`) opens `CancelSaleModal` — admin password required unless the logged-in user already is Admin (`requiresAuth={!user.isAdmin}`), same `admins` list/picker pattern as `CancelCreditPaymentModal`, but no "motivo" field (`Plans/PLANO.md` doesn't ask for one on this action, unlike cancelling a Crediário payment). Once cancelled, `SaleDetailModal` shows a red banner ("Venda cancelada em {data} por X (autorizado por Y)") in place of the button, same shape as the cancelled-payment display in Devedores.

## Key components (`src/components/`)

- **Button / Modal / ConfirmModal / Card** — generic primitives, styled from theme tokens only (see `CLAUDE.md`'s Theme rule). `Modal` closes on `Escape` whenever it's `dismissible` and has an `onClose` (same condition as the ✕ button/backdrop-click) — a modal that shouldn't be Esc-able (or click-outside-able) passes `dismissible={false}` and no `onClose` instead of fighting this default. `size="lg"`/`size="xl"` (default `sm`) are the opt-ins for content that needs more width than the standard dialog (`lg`: `KeyboardShortcutsModal`; `xl`: `ImportCsvModal`'s review screen).
- **ThemeSwitcher** — renders one segment per entry in the `THEMES` catalog (`src/theme.ts`) — never hardcodes "light"/"dark", so adding a theme there is enough (see `CLAUDE.md`'s Theme rule).
- **LockScreen** — the idle-lock overlay `AuthGate` renders on top of whatever screen is open (re-enters the same logged-in user's password via `verify_password`; the screen underneath keeps its state, it's just covered). Also offers "Sair e trocar de usuário" (behind a `ConfirmModal`, since it discards whatever was in progress) for when the locked user isn't around and someone else needs the machine — calls `AuthGate`'s `handleLogoutFromLock`, which resets its own `locked` state *and* logs out, in that order; skipping the reset would leave `locked` stuck `true` and immediately re-show this same screen over the next person's fresh session, since `AuthGate` never unmounts on logout (only its return value switches to `<LoginPage/>` while `user` is `null`).
- **Form-modal `dirty` computation** (see `CLAUDE.md`'s Form-modal rule) — a plain boolean expression comparing each field's current state to the `initial` prop's value (or the empty/default value when creating), recomputed every render; no snapshot/diff library, no per-field "touched" tracking beyond that. `ItemFormModal.salePriceTouched` is a separate, narrower flag (only gates the auto-suggested sale price, see below) — don't conflate the two.
- **MoneyInput** — see `CLAUDE.md`'s Money field rule.
- **PhoneInput** — Brazilian phone mask (`(XX) XXXX-XXXX` fixo / `(XX) XXXXX-XXXX` celular), applied progressively as digits are typed. Same digit-buffer shape as `MoneyInput` (always appends/removes from one end rather than trying to track a caret position mid-string) but formatting-only — never blocks on a digit count other than 10/11, since phone is optional and varies (ramal, formato antigo). Used by `ClientFormModal` and the inline quick-add in `PaymentModal`.
- **Checkbox** — styled checkbox (box + check icon), replaces the raw browser control everywhere a checkbox appears.
- **Tooltip / InfoTooltip** — `Tooltip` renders its popup through a **portal to `document.body`**, positioned from the trigger's `getBoundingClientRect()` (flips above/below depending on available space) — not a plain absolutely-positioned child, because the badge/hint often sits inside an `overflow-hidden` container (e.g. a rounded table wrapper) that would otherwise clip it. `InfoTooltip` is just a `Tooltip` wrapping a small "?" button.
- **StockBadge** — critical/warning/ok chip (`stockStatus()` in `lib/api.ts`: critical when quantity <= minimum, warning up to `lowStockWarningThreshold`, no alert with no minimum set). Wraps itself in a `Tooltip` explaining the numbers behind the status (current quantity vs. `min_quantity` and, for the yellow state, the computed warning threshold) — skipped entirely for the "ok" state, nothing to explain there.
- **ItemFormModal** — Admin-only full item CRUD. On **creation only**, `sale_price` is pre-filled from `cost_price * (1 + default_profit_margin_percent / 100)` (`suggestedSalePrice`, fetched via `getDefaultProfitMargin()`) and keeps recalculating as `cost_price` changes, until the admin edits `sale_price` by hand (tracked by a local `salePriceTouched` flag) — never touches an existing item's price. Also shows a non-blocking warning (text + both price inputs' border) when `sale_price < cost_price`.
- **StockAdjustModal** — the Usuário comum equivalent: add-stock entry (positive delta only) and deactivate, no price/name/category fields.
- **CategoryManagerModal** — Admin-only category CRUD, opened from within `ItemFormModal`'s category `<select>`.
- **ImportCsvModal** — Admin-only, opened from Estoque's "Importar CSV" button (its sibling "Exportar CSV" button has no modal of its own — it just runs `@tauri-apps/plugin-dialog`'s `save()` then `exportItemsCsv`, inline in `InventoryPage`). Three steps in one component, switched by local `step` state: `"pick"` (`open()` file dialog, then `previewItemsCsvImport` — read-only, nothing written yet), `"review"` (the summary screen from `Plans/PLANO.md`'s "Importação de CSV" — novos/alterados/ausentes sections, `size="xl"`), `"result"` (counts after `applyItemsCsvImport`). The backend's `missingItems` is a snapshot from before any remapping — a "new" row the admin links to an existing item (via its own suggestion or `RemapComboBox` below) makes that item no longer missing, so `ImportCsvModal` recomputes the *effective* missing list client-side (`preview.missingItems` minus every item id currently targeted by `remap`) instead of trusting the backend's list as-is once the admin starts remapping. A remapped row is sent to `apply_items_csv_import` as an update with `keepExistingName: true` (see `docs/commands.md`), never as a create.
- **RemapComboBox** (private to `ImportCsvModal.tsx`, not its own file — only used here so far) — the "vincular a item existente" field for a "new" row: an autocomplete instead of a plain `<select>` listing every item, since that stops scaling once the catalog has more than a handful of items. Ranking comes from `lib/itemSearch.ts`'s `itemSearchSuggestions` (see below), capped to 8 results while typing; with an empty, focused query it shows the first 3 items instead of nothing — not real search results, just a peek so the admin knows what the field lists and that it's searchable, before typing anything. Collapses to a "code — nome" chip + "Desvincular" once something's picked — unlike `ItemFilterCombobox` (below), which stays a persistent filter instead of collapsing.
- **`lib/itemSearch.ts`'s `itemSearchSuggestions`** — the "starts with" > "contains" ranking (accent/case-insensitive `normalize()`, same as `SalesPage`'s item search), extracted once a second item autocomplete needed the exact same logic. Shared by `RemapComboBox` and `ItemFilterCombobox`.
- **ItemFilterCombobox** (`src/pages/reports/`) — the item-filter counterpart of `RemapComboBox`: same `itemSearchSuggestions`-driven dropdown, but closed it just shows the selected item's "código — nome" (or an `allLabel`, default "Todos os itens") as the input's own value instead of collapsing to a chip, since it's a persistent toolbar filter, not a one-time "link this row" action. The dropdown always lists `allLabel` first, above the matching items, as the "clear this filter" option. Used by `MovimentacaoEstoquePage` and `HistoricoPrecoPage`'s item filters (both used to be plain `<select>`s, same scaling problem `RemapComboBox` solved for CSV import).
- **UserFormModal** — create/edit user; disables the Administrador/Ativo checkboxes when editing your own row (backend also rejects it, see `CLAUDE.md`'s Auth rule) and shows the "elevate to Admin" confirmation before saving when toggling a non-admin user's checkbox on.
- **DiscountModal** — item or order-level discount (% or R$), used from `SalesPage`. Only shows the admin-picker + password fields when `requiresAuth` is true (see the Venda/PDV section above); otherwise applies directly. The %/R$ switch is keyboard-reachable too: `←`/`→` toggle it, but only while the value field is still empty — the moment there's a digit in it, arrow keys go back to normal caret movement instead of hijacking the field. Submitting a `0` (or a blank field, which parses to `0`) is treated as removing the discount rather than applying a meaningless "-0%"/"-R$ 0,00" — same path as clicking "Remover desconto", no admin auth required either way.
- **PaymentModal** — payment method picker (Dinheiro/Cartão/PIX, plus Crediário when `creditEnabled`) shown when finalizing a sale, see the "Devedores"/Venda sections above for the inline client step. The methods are a roving-tabindex radiogroup: `←`/`→` move both the selection and focus, and `Enter` submits directly from a focused method button (a focused `type="button"` only re-fires its own click, it doesn't submit the form on its own, so this is handled explicitly rather than relying on native form-submit-on-Enter). The first method auto-focuses on open — without it, keyboard focus would stay on `SalesPage`'s hidden search input behind the modal and nothing in here would respond to the keyboard at all, the same root cause fixed in `ReceiptResultModal` below. When the selected Crediário client has a negative `balance` (store credit), the "Valor pago agora" `MoneyInput` doesn't show at all — instead a green box says "Cliente possui saldo com a loja" and the credit is applied automatically (`min(storeCredit, total)`, computed as `effectiveCreditPaidNow`), with no manual amount to type. If that covers the sale's full total, the message says so and the sale is sent with `creditPaidNow === total` — allowed only in this exact case (see `create_sale` in `docs/commands.md`), everywhere else Crediário requires `paid < total`. Both the selected-client card and the suggestion list show "Crédito com a loja: X" instead of a raw negative "Saldo atual" when this applies. Selecting a client (via Enter on the search box, a suggestion click, or "Salvar e vincular" on a freshly-cadastrado one) unmounts the search input — a focused node being removed drops focus to `<body>`, silently swallowing the next `Enter` in an all-keyboard flow (search → select → Enter to finalize). Fixed the same way as the method-buttons quirk above: the "Valor pago agora" `MoneyInput` has `autoFocus` so it grabs focus the moment it mounts (letting `Enter` inside it hit the form's native submit-on-Enter, since `MoneyInput` deliberately doesn't `preventDefault` that key); when store credit covers everything and no input renders at all, a `useEffect` on `[selectedClient, hasStoreCredit]` focuses the "Finalizar" button (`Ref<HTMLButtonElement>`) directly instead — `Button` now accepts `ref` as a plain prop (React 19, no `forwardRef` needed).
- **ClientFormModal** — create/edit devedor (Nome\*, Telefone, Data de lembrete, Observação), same dirty-check-before-close pattern as `ItemFormModal`/`UserFormModal`. Self-service for any profile — **except** renaming a client that currently has an open Crediário balance, which reveals the same admin password + admin `<select>` shape as `DiscountModal`/`CancelCreditPaymentModal` (`needsAuthUI = nameChanged && clientHasDebt && !user.isAdmin`, pre-verified client-side via `verifyPassword` before the real backend call). Editing phone/lembrete/observação, or renaming a client with no open balance, never shows this.
- **CreditPaymentModal** — pays off the sale(s) the caller passed in via `selectedSales` (`MoneyInput`, "Quitar tudo" shortcut sets the field to their combined `remaining`); typing past that sum clamps to it instead of blocking with an error (`MoneyInput`'s `max` prop). When the amount is less than the sum and more than one sale was selected, shows a residual-sale radio picker (disables an option whose `remaining` is smaller than the shortfall, since it can't absorb that much) — with a single sale selected there's nothing to choose, that sale is the residual one automatically.
- **CancelCreditPaymentModal** — soft-cancels a mistakenly-registered payment (motivo textarea, required); reuses `DiscountModal`'s admin-authorization shape (password + admin `<select>`, pre-verified client-side via `verifyPassword` before the real backend call) since reversing a payment is treated as sensitive even though registering one isn't. Spells out the consequence up front — "Essa ação vai aumentar o débito de X para Y, já que você está cancelando o pagamento de Z" (`Y = client.balance + payment.amount`) — rather than leaving the operator to infer it from the numbers on the previous screen.
- **SaleDetailModal** — sale lookup by id (`get_sale_detail`), used by both Devedores' "Ver venda" and Histórico de vendas; renders the same receipt-style item/total layout as `ReceiptResultModal` but without any of its post-sale actions (Imprimir/Nova venda) — this modal isn't reachable from an in-progress sale. Shows "Cancelar / estornar venda" (opens `CancelSaleModal`) while the sale is still `completed`, or a red "cancelada" banner once it isn't; takes `admins`/`requiresAuth` props from the caller and an optional `onCancelled` so the caller's own list/detail can refresh too.
- **CancelSaleModal** — cancels/estorna a sale (`Plans/PLANO.md`'s "Cancelamento / Estorno de venda"); same admin-authorization shape as `CancelCreditPaymentModal` but no "motivo" field, since that action doesn't require one. The backend only reverses stock — for a Crediário sale with money already applied to it, that amount becomes floating credit for the client instead of being reversed (see `docs/database.md`). For a Crediário sale, fetches the client's current balance (`getClientDetail`) to spell out the exact consequence up front — "Essa ação vai reduzir o débito de X de Y para Z, já que a venda de W será cancelada" (`Z = client.balance - sale.total`) — plus a separate note when `sale.creditPaid` is set, since that amount specifically isn't reversed. Same "state the consequence with real numbers" pattern as `CancelCreditPaymentModal`.
- **ContextMenu** — generic fixed-position menu (clamps itself inside the viewport, closes on outside click/Escape/window blur) — positioning is just `{x, y}`, so it's not tied to right-click specifically. The app disables the browser's own context menu globally (`main.tsx`), so right-click is free for this component wherever it's wired up that way (Estoque's item rows, Usuários' rows, `CategoryManagerModal`'s category rows), with the same actions already available through the row's buttons, resolved per row/profile by the caller. Histórico de vendas instead triggers it from a visible "⋮" button's click coordinates (see below) — a deliberate exception to the right-click convention, since a POS app may run on a touchscreen where right-click doesn't exist.
- **StockBrowserModal** — see Venda/PDV's "Estoque browser" bullet above.
- **ReceiptResultModal** — post-sale result screen (receipt preview, Imprimir/Abrir pasta/Nova venda), non-dismissible except via "Nova venda" so the cashier doesn't lose the just-completed sale by clicking outside. "Nova venda" auto-focuses on open (same reasoning as `PaymentModal` above). `Modal`'s built-in Escape-to-close is off here on purpose (`dismissible={false}`), but `Esc` still triggers "Nova venda" via a dedicated listener — the sale already committed by this point, so there's nothing to lose by treating Esc as "move on" instead of leaving it dead.
- **KeyboardShortcutsModal** — opened from a "?" button next to Venda's shortcut hints (`Modal`'s `size="lg"`, the one modal wide enough for this). Renders a full keyboard diagram (function row, main alphanumeric block, nav cluster, arrow cluster, numpad — built from `KeySpec` row arrays plus a CSS-grid numpad for its 2D-spanning `+`/`Enter`/`0` keys) with the keys Venda actually uses highlighted, so someone who doesn't know a key by name can visually match the highlighted spot to their physical keyboard. A legend below spells out what each highlighted key does.
- **Kbd** — the "keycap" chip used for every inline shortcut hint (Venda's shortcuts bar, the Esc hint in `PaymentModal`/`DiscountModal`) — matches the mockup's `.kbd` class (bordered chip, thicker bottom border for a pressed-key look) via theme tokens.
- **Pagination** — "X–Y de Z" + numbered pages (with first/prev/next/last and an ellipsis for gaps beyond the current page's immediate neighbors), purely client-side (the caller already has the full list, just slices it). Renders nothing when everything fits on one page, unless `pageSizeOptions`/`onPageSizeChange` are passed — those add a page-size `<select>` and keep the bar visible regardless of page count, so the choice stays reachable. Used by Devedores' two histories (5 rows/page, fixed, no size selector), Estoque and Histórico de vendas (10/20/50, selector shown).
- **Toast / ToastContainer** (`src/components/Toast.tsx`) — generic, stackable notification card (bottom-right corner, newest at the bottom of the stack), rendered by `ToastProvider` (see "Context" below). Three types (`success`/`warning`/`error`), each with its own icon/color; a title line, an optional second line that's either plain text or (with `onClick`) a clickable action (used for "Clique aqui para abrir a pasta" after a CSV/PDF export, wired to `openContainingFolder`), and a "×" to dismiss. Auto-closes after `duration` (default 60000ms) via `setTimeout`, with a footer bar that visually counts down to that close — rendered full-width then flipped to `width: 0` a frame later (`requestAnimationFrame`) so the shrink is an actual CSS `transition`, not an instant snap; this is also the only signal the countdown needs; no separate numeric timer.

## Context (`src/context/`)

- **AuthContext** — `{ user, loading, login, logout, setUser }`; calls `get_active_user` once on mount. A separate `useEffect` on `user` itself (not folded into `login`/`logout`) calls `setLoggerUser` from `src/logger.ts` whenever it changes, by whatever path — `login()`, `logout()`, the initial `getActiveUser()` fetch, or a page calling the raw `setUser()` directly (e.g. after changing theme/auto-lock) — so every log line stays tagged with whoever's actually logged in, without each call site needing to pass it in.
- **ThemeContext** — see `CLAUDE.md`'s Theme rule for how it reconciles `localStorage` (pre-login) with `users.theme` (post-login).
- **NavigationGuardContext** — one function, `(dirty: boolean) => void`, provided by `AppShell` around its `<Outlet/>` and consumed by a page via the `useNavigationGuard(dirty)` hook (auto-clears on unmount, so leaving a route never leaves a stale warning for whichever page loads next). Currently only `SalesPage` uses it (`cart.length > 0`) — see `AppShell`'s bullet above for what the sidebar does with it.
- **ToastContext** — mounted once at the app root (outermost provider in `App.tsx`, above `AuthProvider`, so it's available even pre-login if ever needed). `useToast().showToast({ type, title, message?, onClick?, duration? })` appends a `Toast` (see "Key components" above) to a local `toasts` array, each with its own `crypto.randomUUID()` id; dismissing (× click, auto-close timer, or clicking a `message` with `onClick`) filters it back out. Generic on purpose — first wired up for every CSV/PDF export's success *and* failure feedback (Estoque, Histórico de vendas, every Relatórios screen — replacing what used to be a per-page `exportError` state + inline banner), each passing its own report name as `title` and, on success, `onClick: () => openContainingFolder(path)`. Also used for other "fire and forget" background actions with no open form/modal to show the error next to: `SalesHistoryPage`'s recibo print/open, and `SettingsPage`'s "abrir pasta de logs" and Crediário on/off toggle. **Not** used for validation-style errors inside an open modal/`ConfirmModal` or the login/lock screens (`ItemFormModal`, `DiscountModal`, `UsersPage`'s delete confirm, `LoginPage`, etc.) — those keep their inline `error` state/banner on purpose, since the error needs to stay pinned next to the field/button while the user retries, not fade out in a corner toast.

## Hooks (`src/hooks/`)

- **useIdleTimer** — resets on `mousemove`/`keydown`/`click`; calls `onIdle` after N minutes. `secondsRemaining` stays `null` until the last 30 seconds before the lock (`AuthGate` uses this to show a warning, not a permanently-ticking countdown — a countdown that resets on every mouse move would just be noise while someone is actively working).
- **useDashboardLayout** — see the Dashboard section above (edit mode, debounced/immediate autosave, undo-via-snapshot).
